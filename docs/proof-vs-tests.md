# 証明とテストの分け方

**どんな入力でも守りたいルールは、そのルールを決める純粋な処理で証明する。ブラウザの入力・表示がその処理につながっているかは、実際のブラウザでテストする。**

## どこで確認するか

| 確かめたいこと | 向いている手段 | ライフゲームの例 |
| --- | --- | --- |
| すべての状態で成り立つ、仕様として安定した約束 | Bend の law と証明 | 生きた近傍が3つなら生存または誕生。2つなら今の生死を維持。それ以外は死ぬ。区画のどのセルでも、必要なら隣の区画も参照し、8近傍を数えた結果に一致する。 |
| 境界条件やデータ表現が、ルールどおりに実装されているか | 単体テスト・参照実装との比較 | 32ビットの区画をまたいで近傍を数える。盤面の外周はつながない。リサイズしても重なる範囲は残す。 |
| 実際の操作が意図した状態変更につながるか | ブラウザテスト | 拡大・スクロール後も狙ったマスをタップできる。移動モードのドラッグは盤面をずらすが、セルは編集しない。 |
| 操作しやすいか、表示が読みやすいか | 実機での目視・操作 | 縦画面でボタンが見切れないか、指で隣のマスを押し間違えないか。 |

## UIでも証明する価値があるとき

「見た目」ではなく、**操作の意味**を証明したいとき。例えば、盤面と表示位置を別の状態として持ち、純粋な状態更新に対して「拡大・移動イベントの前後で、盤面のセル配置は完全に同じ」と書ける。生存数だけの比較では、1セル消して別の1セルを増やすバグを見逃す。再生中にタイマーで世代が進むのは別イベントなので、この約束の対象外にする。

また、何もしない実装でも「盤面を変えない」は満たせる。移動のテストでは「盤面は同じ」に加え、「動ける方向にドラッグすると表示位置が変わる」も確かめる。仮にこの状態更新を証明しても、ブラウザが移動を配置イベントとして渡していないかは別にテストする。

**このプロジェクトの現状：** [`LAWS.bend`](../LAWS.bend) にあるのは、セル遷移がConwayのルールに従うことと、有限盤面で32セル分の更新が参照版と一致することの2つです。

区画内の任意の有効な列と、隣接する9区画から得る出力全体の一致は [補助の証明](../core/proof-checks.bend) として残しています。実装は3行を同時に走査し、参照版は上3・横2・下3セルの値を読んで数えます。盤面の端は四辺までの距離で判定し、斜めは縦横どちらかが外なら死セルにします。

Web側が正しい区画や距離を渡すこととリサイズは `node web/test.mjs`、Mac版の盤面・操作・描画は `node desktop/native-test.mjs` で確認します。拡大・移動で盤面が変わらないという例は、今はLAWにしていません。

## 上流ベンチマークから取り入れた例

[Bend公式の Game of Life ベンチマーク](https://github.com/bendlang/bend/blob/6180be5b21c4af6895395b27ad3cde026909364e/bench/runtime/gameoflife/main.bend#L71-L89) は、1世代後に同じなら静止、1世代後に変化して2世代後に戻るなら周期2として数える。確認した上流のディレクトリには専用の `LAWS.bend` はなく、これは分類処理。上流の盤面は端がつながる4×4だが、このプロジェクトには端がつながらない盤面で同じ観点を適用した。

`core/pattern-spec.bend` は、中央に32ビット区画の継ぎ目を持つ64×5の盤面を用意し、実際の有限盤面の更新関数 `next_bounded` を呼ぶ。2×2ブロックは1世代後も同じ。ブリンカーは1世代後に横から縦に変わり、2世代後に横へ戻る。これらは特定の初期配置の証明で、任意の盤面の周期やブラウザ側の配線を証明するものではない。
